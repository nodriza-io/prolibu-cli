# Promotion model

How `promote.js` moves each kind, and why. Every rule was checked against the platform's
model code and on a test account (promoting objects into the same account under new
`qa-skills-` keys).

## The bundle

`export` writes one JSON file (mode 600) in the session's temp folder:

```json
{
  "format": "prolibu-config-bundle",
  "formatVersion": 1,
  "source": "<source domain>",
  "selection": {"items": [], "kinds": [], "dependencies": true},
  "objects": [
    {"kind": "endpoint", "key": "orders", "name": "Orders",
     "data": {"routeName": "orders", "script": {"$ref": {"model": "Script", "key": "scriptCode", "value": "orders-dev", "at": "script"}}},
     "setByHand": [], "warnings": [], "unresolved": []}
  ],
  "hash": "<hash of objects>"
}
```

- Every id is replaced by a `$ref` with the referenced record's model and stable key.
- Fields the platform sets (`_id`, `createdAt`, `updatedAt`, `createdBy`, `updatedBy`,
  `workspace`, `refId`, `refUrl`) are dropped. The target sets its own.
- The `hash` covers `objects`; an edited bundle is refused. To change a value, use
  `--override`; to change a key, use `--map`.
- Objects are ordered so that what is pointed at is created first (content templates and
  scripts, then filters and templates, then endpoints and forms, then webhooks and custom UI).

## References

| Model | Found in the target by |
| --- | --- |
| User | `email` |
| UserGroup | `userGroupCode` |
| Role | `keyname` |
| Stage | `stageCode` |
| Script | `scriptCode` (after `--map`) |
| ContentTemplate, MessageTemplate, Form | their code (after `--map`) |
| File | not copied: removed and listed in `setByHand` (re-upload) |

Known reference fields are read as their model (`endpoint.script`,
`authentication.requiredRoles[]`, `form.assignmentGroup`, `mappings[].assignmentGroup`,
`submissions.notifyOnSubmit[]`, `presentation.layout`, `assignee`, `collaborators[]`). Any
other 24-hex value (inside a filter, a form's defaults) is probed in the source in this order:
Stage, User, UserGroup, Role, Script, ContentTemplate, MessageTemplate, Form, File. An id that
is none of them stays `unresolved` and blocks the object in the target.

Only what an object **owns** is exported with it: an endpoint's script and an e-mail
template's layout. Stages, users, groups and forms it points to must already exist in the
target or be selected explicitly. This keeps a filter from dragging its pipeline along.

## Secrets: never copied

| Where | What happens |
| --- | --- |
| Script `variables` | Only the keys travel. A new script gets the keys with empty values; an update leaves the target's variables alone and lists keys the target lacks. |
| Webhook `headers` | Only the names travel. A new webhook gets no headers; an update keeps the target's. Set values with `prolibu-webhooks` (`generate: true`). |
| Webhook `endpoint` | Not exported: the destination of production is a decision, passed with `--override`. Checked as public https (same rule as `prolibu-webhooks`). |
| Form `access.password`, `access.serviceCredential` | Dropped. A new password form gets a password generated by the server. |
| Code and HTML | Copied as they are, but scanned: a key-looking literal (`apiKey = "…"`, `Bearer …`) or the source domain gives a warning (the value is never printed). |
| Endpoint | Holds no secret; shared secrets for signatures live in its script's variables. |

## Per kind

**script.** Fields copied: name, readme, code, `flow`, hooks, schedule, quote-calculation
flag, timeout, `git`, assignee and collaborators. The server checks code syntax and the cron
expression on save, and rejects hooks for an object without lifecycle hooks on in the account;
the preview checks the target's preferences first. A script that runs by itself (hooks,
schedule, quote calculation) starts working as soon as it is saved active, so it is created
off; turning it on is a separate step. An endpoint-only script keeps the source's `active`.

**endpoint.** Key `routeName` (unique in the account); `endpointCode` is random and dropped.
The script reference resolves to the target script (or the one created in the same apply).
`authentication.enabled: false` is flagged as public. On a production target, a script key
ending in `-dev` is flagged.

**form.** Key `formCode`; the server accepts a code on create. `endings` and `metaMapping` are
deprecated and dropped; `type: "meta"` forms are refused (they belong to an ad hub). The merged
form is checked with `prolibu-forms`' `checkForm` against the target's fields
(`/v2/form/getmodelfields/<Model>`): its errors block, its warnings pass through.

**webhook.** Event names are matched against the target's catalog and selected fields against
the target's columns (helpers of `prolibu-webhooks`). The server requires a unique
`endpoint` per account.

**stage.** Key `stageCode`. `protected` is dropped. `requiredFields` and `suggestedFields` must
be columns of the stage's model in the target (`/v2/service/getschema?type=columns`); the
server rejects unknown fields too. A target stage with another `stageType` blocks. Factory
stages carry `protected`, a list of the fields that may change (`-requiredFields …`); any
other changed field answers 403 on the server, so the preview blocks it. A stage with
`setAsDefault` is flagged.

**messageTemplate.** Derived and sync fields are dropped (`contentText`, `bodyPreview`,
`whatsappStatus`, `syncStatus`, `rejectionReason`, `meta`). `channel` is dropped: a WhatsApp
template saved with a channel and a body is pushed to the provider for review. A target
WhatsApp template that already has a channel or provider id is not changed when the text
differs (that re-submits it and loses the approval). `assets` (embedded image files) are not
copied; the HTML keeps pointing to the source files.

**contentTemplate.** `assets`, `library` (points to a deal) and `defaultLayout` (one per
workspace) are dropped.

**customFilter.** `filter` ids are rewritten (stages, users…).

**customUi.** Its `code` runs in the browser of every user; created off. Icon files are not
copied.

**report, dashboard.** Compared only (ids left as they are). Reports point to pages and to
other reports by id, dashboards to widgets; rebuild them with `prolibu-dashboards`, whose tools
validate on the server.

**customField, cob.** Compared only. Saving either restarts the account's servers. Custom
fields are compared one by one: `missing in the target`, `different`, `only in the target`.

## Diff and version

- Merged sub-objects (`authentication`, `access`, `thankYou`, `submissions`, `uploads`,
  `presentation`, `scheduledTask`, `allowEveryone`, `git`, `display`, `sideBar`, `rowAction`,
  `fieldWidget`, `cellWidget`, `defaultColumns`, `retargeting`) compare as a subset: the server
  merges them and adds defaults. Everything else compares exactly.
- A field the source does not have is never removed from the target.
- The version hashes the bundle, the target domain, every step's action and body, and the
  target records' `updatedAt`. `apply` rebuilds the plan and refuses when it differs.

## Production

A target whose first label is not `dev`/`devN`, `stg`, `staging`, `qa` or `test` is treated
as production (the shared helper's rule). The preview adds a `WARNING` and `production: true`;
`apply` refuses without `--to-production`, before reading anything.
