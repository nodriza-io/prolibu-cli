# Proposal and contract model

Reference for `prolibu-proposals`. Verified against the server code, the app's code and a
live test account. Read the section you need.

## The deal's proposal

`Deal.proposal` is a sub-document of the deal, not a record of its own:

| Field | What it is |
| --- | --- |
| `enabled` | On or off. Off, the viewer answers "Deal does not have a proposal." |
| `title` | Shown on the document. Required when `enabled`. |
| `template.layout` | `_id` of a ContentTemplate with `templateType: "layout"`. |
| `template.layoutHtml`, `snippetHtml` | HTML burned in by the server from the layout and the quote lines. Never send them. |
| `template.language`, `defaultFont`, `embeddedFonts`, `assets`, `customContent` | Document language, fonts and custom content. The app copies `language` from the layout's `taxonomy.language`. |
| `quote` | The quote. Only through `prolibu-quotes`: a save replaces it whole. |
| `attachments` | Files shown with the proposal. |
| `expirationDate`, `unpublishedDate` | Filled from the account settings when the proposal is turned on, if missing. |
| `createdAt` | Set by the platform when first turned on. |

Other deal fields: `proposalVersions` (`refs`, `details`, `restorationPoint`), `contracts`
(ids of Contract records), `tracking` (client views; read only).

### Saving rules

- Turning on requires a `contact` and a `title`: 400 "Contact is required for proposal." /
  "Proposal title is required.".
- A `PATCH` with `proposal` merges `proposal.template.*` key by key; `quote` and
  `customContent` (free-form fields) are replaced whole. `null` removes a field.
- When `template.layout` arrives without `layoutHtml`, the server copies the layout's `html`.
  With `layoutHtml` in the payload it copies nothing. It does not check the template type: a
  `snippet` or `content` id is saved as the layout.
- With no layout at all, the server takes the first quote line's product layout
  (`proposalTemplate.layout`), else the user's default layout (workspace, then company, then
  the account's global layout; `GET /v2/contenttemplate/defaultLayout`).
- When the payload carries `proposal.enabled: true` and no `stage`, and the account has
  `modules.sales.deals.stageRules.defaultProposalStage`, the deal moves to that stage, on every
  such save (stage notifications follow). Readable by every user at `/v2/user/preferences`.
- `{{ }}` in the title is compiled with the deal's data (plus the contact's full name and
  company) and saved compiled.
- Each save that touches `proposal` asks the print service for a new thumbnail (no effect on
  the data).
- A deal in an end-of-flow stage rejects changes to `proposal` and `proposalVersions` unless
  `stageRules.allowEditInEndFlowStages` is on.

## The document and the PDF

- The proposal viewer renders the document in the browser from the deal: layout, custom
  content, quote snippets. The API has no endpoint that returns the proposal's PDF.
- Viewer link: `https://<domain>/ui/spa/view/deal/<dealId>/<contactId|none>`. With `none` no
  view is recorded. With a real contact id the open counts as a client view: it updates
  `tracking` and notifies the owner. Use `none` for internal previews.
- The PDF is printed by the platform's print service from that viewer. Users print or
  download it from the viewer when the account allows it
  (`modules.sales.deals.proposalPrintAndDownload.user|client.allowDownload|allowPrint`).
- Client links are made by the app's Share action (short link, QR, e-mail, WhatsApp, follow-up).
  They create records and may e-mail people: never from a skill.

## Versions (`ProposalVersion`)

- Fields: `proposalVersionCode` (`PPV-…`), `dealSource` (the deal), `proposalData` (a copy of
  `proposal`), `sha256`. No generic create or update.
- **Create:** `POST /v2/proposalversion/createRestorationPoint`
  `{dealSource, proposalData, versionName?, visibleToClient? (false), insertIndex?}`. The
  version is what the caller sends; the app sends the proposal on screen. Missing `template`
  is taken from the deal, missing `layoutHtml` from the layout, and the quote is
  recalculated. `proposalData.enabled` must be true. It answers `{details}` and appends the
  version to `refs` and `details` (at `insertIndex` when given).
- **Automatic versions:** with the account setting `proposalVersioning.autoGenerate`, every
  deal save that carries `proposal` (on an enabled proposal) creates a hidden version named
  after the date, `isAutoGenerated: true`, holding the proposal after the save.
- **List:** `details` on the deal: `{id, versionName, visibleToClient, isAutoGenerated,
  createdAt, creator, sha256}`. The entry with `id: null` / `latestVersion: true` is the live
  proposal ("Latest Version" in the account's language); its name cannot be changed.
- **Restore:** `PATCH /v2/deal/<id>` `{proposalVersions: {restorationPoint: <versionId>}}`.
  The server replaces `deal.proposal` with the version's `proposalData` (only versions of that
  deal). No copy of the current proposal is made.
- **Publish:** setting `visibleToClient` in `details` shows a version to the client. The app
  writes the whole `details` array; a partial array removes versions. At least one entry must
  stay visible. Publishing is the app's job.
- **Delete:** `DELETE /v2/proposalversion/<id>`, only with `proposalVersioning.allowDeleteVersions`.
- On a closed deal, `createRestorationPoint` creates the version record and then fails to list
  it on the deal: an orphan. The script blocks closed deals first.

## Contract templates

- A contract template is a Contract with `isContractTemplate: true`. The app's "Save as
  template" sends `{contractName, contractEditor, isContractTemplate: true, status: "Draft",
  signers: []}`. Templates never send e-mails and hide `status` and `signers` in the app.
  Favorites carry `index`.
- `contractEditor` is the body (HTML). A template may also carry fixed `contractDocuments`
  (PDFs), a `header` (`html`, `showPageNumber`), `signatureSlots`, `language`.
- List: `GET /v2/contract?xquery={"isContractTemplate":true}`.

### Body syntax

The same shared code (`/js/SharedContractUtils.js`, version 2.5.0 at the time of writing) fills
the body in the app and on the server:

1. **`[[field]]`** is replaced from a flat map of the deal. Lookup: exact name, then any case,
   then a dotted path. Names:
   - Contact: `full_name`, `nombre_completo`, `client_name`, `first_name`, `nombre`,
     `last_name`, `apellido`, `email`, `correo`, `phone`, `telefono`, `mobile`, `celular`,
     `whatsapp`, `identification`, `cedula`, `cedula_de_identidad`, `documento`,
     `document_number`, `address`, `direccion`, `direccion_completa`, `city`, `ciudad`,
     `state`, `estado`, `country`, `pais`, `zip`, `codigo_postal`, `job_title`, `cargo`.
   - Company: `company_name`, `empresa`, `nombre_empresa`, `nit`, `company_id`.
   - Deal: `deal_name`, `negocio`, `nombre_negocio`, `deal_code`, `proposal_title`,
     `titulo_propuesta`, `amount`, `valor`, `monto` (formatted, rounded, for example
     `$22,817 USD`), `currency`, `moneda`, `valor_en_letras`, `monto_en_letras` (Spanish, upper
     case), `amount_in_words`.
   - Dates (`DD/MM/YYYY`, UTC): `fecha_actual`, `current_date`, `today`, `hoy`,
     `fecha_creacion`, `created_date`.
   - Owner (the deal's assignee): `vendedor`, `sales_rep`, `owner_name`, `owner_email`.
   - Dotted paths of the deal: `contact.mobile`, `company.companyName`, `proposal.title`…
   The amount comes from `proposal.quote.total` and the currency from `quote.quoteCurrency`.
   A name with no data prints empty; a name that does not exist is **removed** from the
   document.
2. **`{{ }}`** is Handlebars, compiled after the fields, with the deal as context plus
   `signers` (array of contacts), `currency`, `locale`, `amount` (raw number). Helpers:
   `toCurrency`, `shortDate`, `toWords`/`enLetras`, `signatureDate`/`fechaFirma`. Example:
   `{{#each signers}}{{firstName}} {{lastName}}{{/each}}`, `{{toCurrency amount}}`. A syntax
   error leaves the whole body uncompiled (raw `{{ }}` in the document). The app's editor turns
   dotted names into links when autolink is on; a link inside `{{ }}` is a syntax error.
3. **Reserved:** `[[firma.N.fecha]]`, `[[firma.N.ubicacion]]`, `[[firma.N.ip]]`,
   `[[firma.N.dispositivo]]` are filled when participant N signs. `⟦sig:N⟧` marks where
   participant N's signature box goes (N counts from 1, in the participants' order).

Only the deal's `contact`, `company` and `assignee` are filled in when the server generates
the contract (one level). A reference of a reference (the contact's company's fields through
`contact.company.*`) stays an id: use the `company`/`company_name` names instead.

## Generating a contract from a deal

Two server paths exist:

| Call | Used by | What it does |
| --- | --- | --- |
| `POST /v2/contract/generateFromDeal` | The proposal viewer's accept-and-sign flow; this skill | Fills the template on the server, prints it, prints the proposal (or the chosen `pages`), merges both into one PDF and creates the contract. `status` only `Draft` or `Ready` (default `Ready`). |
| `POST /v2/contract/generate` | The app's generate-contract dialog | Expects the caller to send the printed PDFs (`files`), else attaches only the proposal PDF. Keeps the body unfilled. `status` defaults to `Ready` and is not validated. |

The skill uses `generateFromDeal` because an API client cannot print the template itself.
Body: `{dealId, contactId, signerContactIds?, contractTemplateId?, attachProposal? (true),
pages?, status}`. With an API key no verification `code` is needed; `contactId` must be one of
the participants. What the server does:

- Requires an enabled proposal and a deal contact. Participants default to the deal's contact.
- Returns the deal's existing contract (`existing: true`) when one exists that is not
  `Rejected` and does not have `skipDealApproval`. Nothing new is created.
- Names it `"<proposal title> - Contract"`, language from the proposal, roles all `signer`,
  `options.reject.allow: true`, `createdBy` = the deal's creator.
- Saves `contractEditor` **filled in** (not re-editable as a template) and `contractFields`:
  the flat names plus the nested contact, company, assignee, quote lines and signers, trimmed
  to what the template uses. `dealSnapshot` keeps a frozen copy of the deal.
- Links the contract to the deal (`origin {modelName: "Deal", docId}` → `Deal.contracts`).
- The response carries a `signingUrl`. Never show or forward it.
- Printing can take tens of seconds. If the print service fails, the contract may be created
  without documents.

## E-signature

- `signers`: contact ids in order. `signerEvidences`: per contact id
  `{fullName, email, mobile, role, status, …evidence}`; on save the server rebuilds it from
  the contacts, so a client sends `{<id>: {role}}` for every participant. Roles: `signer`,
  `reviewer`. Entries for ids not in `signers` are dropped. `signers` and `signerEvidences`
  are written before the rest of the save is validated.
- `options`: `sendEmailsInOrder`, `verification.emailCode`, `deadlineDate`, `reject.allow`,
  `skipLocation` (merged key by key on `PATCH`).
- `placeholders` / `signatureSlots`: where each signature goes, per document and page. The
  app derives them from the `⟦sig:N⟧` boxes; contracts generated from a deal are re-printed
  when someone signs. Check positions in the app before sending.
- **Sending:** when a non-template contract is saved with `status: "Ready"`, at least one
  participant and at least one document, the server e-mails the participants (only the first
  with `sendEmailsInOrder`). This happens on create and on **every** later save while it is
  `Ready`, except saves that only touch `tracking`, `deadlineNotifiedFor` or `assets`.
  Moving to `Ready` explicitly requires participants and documents.
- `POST /v2/contract/resendEmail/<contract>/<signer>/<single|all>` e-mails the participants
  whatever the status, **even for a Draft** (it only checks that there are participants).
- Also send e-mails: `POST /v2/contract/sendCode/…` and `POST /v2/contract/sendVerificationCode`.
  Public signing actions: `PUT /v2/contract/sign/…`, `PUT /v2/contract/reject/…`. When
  everyone signs, the deal moves to Approved unless `skipDealApproval`.
- Status flow: `Draft` → `Ready` (sent) → `Pending` (first signature) → `Signed` / `Rejected`.

## Other objects people may mean

| Object | What it is |
| --- | --- |
| `ContentTemplate` | Document templates: `layout` (whole proposal), `content`, `snippet` (a quote line's block), `certificate`, `customView`. |
| `MessageTemplate` | E-mail, WhatsApp and text templates (Handlebars). Not proposals. |
| `Template` | Server-side e-mail and page templates. Not used by proposals. |
| `Presentation` | A document for a contact with a `layout`, without a deal or quote. |
| `ProposalWizard` / `ProposalWizardGroup` | Public self-service quoting pages (`/pw/<code>`) that create deals with a proposal. |
